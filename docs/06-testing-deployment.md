# 검증과 Vercel 배포

이 문서는 구현 후 무엇을 확인해야 완성이라고 할 수 있는지 정한다. 로컬 실행과 테스트 명령은 [README.md](../README.md)에 있다. 실제 키·DB 프로젝트·배포 URL을 사용한 외부 연동 검증은 로컬·대체 응답 테스트와 구분한다.

## 1. 단계별 작업과 통과 조건

| 단계 | 할 일 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 1 화면 | HTML·CSS·모바일 배치·빈 상태·피드백 폼 | 375px·1440px에서 읽기·키보드 조작 가능 |
| 2 이미지 처리 | 샘플과 실제 첨부로 정규화·격자·팔레트·PNG | 정해진 해상도, 블록 크기, 색상 상한 확인 |
| 3 피드백 | 개발 Supabase SQL·API·목록·중복 전송 | 실제 저장·새로고침 후 조회·전체 페이지 확인 |
| 4 AI | OpenAI 생성·편집과 오류 처리 | 실제 각 1회 성공, 결과 가공·다운로드 확인 |

순수 함수와 API 오류 테스트에는 가짜 응답을 주입해 외부 비용 없이 검증한다. 이런 테스트와 실제 OpenAI·Supabase 통합 결과를 구분해서 기록한다. CSS 값 하나마다 테스트를 만들기보다 사용자 결과와 데이터 보존에 영향을 주는 동작을 검증한다.

## 3. 픽셀 결과를 수치로 확인하는 방법

1. 다운로드 PNG가 PNG 시그니처이며 가로·세로가 1024인지 확인한다.
2. N=64이면 16×16 단위 정사각형 안의 모든 픽셀 RGB가 같아야 한다. N=32는 32×32, N=128은 8×8 블록으로 같은 검사를 한다.
3. K=16/32이면 전체 고유 RGB 수가 각각 16/32 이하인지 확인한다. alpha는 모두 255다.
4. 같은 AI 소스와 같은 옵션을 반복 처리하면 PNG의 디코딩 픽셀이 같아야 한다. 브라우저 간 PNG 압축 바이트 일치까지 요구하지 않는다.
5. 미리보기의 Blob과 다운로드 Blob이 같은 객체 또는 같은 픽셀 내용인지 확인한다.

이 검증은 사진을 모자이크처럼 보이게 하는 CSS 효과만으로 기능 완료를 주장하는 것을 막는다. 스타일 품질은 별도 육안 점검으로 대상의 구분, 픽셀 경계, 색상 조화, 원본의 주요 특징을 확인한다.

## 4. Supabase 준비

1. 개발 프로젝트를 만들고 프로젝트 URL과 서버 secret key를 확보한다.
2. `001_feedback.sql`, `002_rate_limits.sql`, `003_feedback_attachments.sql`을 순서대로 적용한다. 운영 DB에는 새 배포 전에 첨부 마이그레이션 적용 여부를 확인한다. [피드백 SQL](05-supabase-feedback.md), [요청 제한 SQL](04-backend-openai.md)
3. 테이블 RLS, 공개 역할의 접근 차단, service_role의 필요한 권한만 허용했는지 확인한다.
4. Supabase Cron을 켜고 카운터 정리 작업을 등록한 뒤 실행 이력을 확인한다.
5. 개발용 글을 실제 API로 저장하고 조회한다. 운영 환경은 별도 Supabase 프로젝트를 권장한다. 한 프로젝트를 공유하면 Preview의 피드백과 요청 제한도 운영 데이터에 섞인다는 사실을 설정 기록에 남긴다.

## 5. Vercel 배포 절차

### Preview

1. 구현 파일과 `package-lock.json`을 준비한다. `.env.local`은 Git과 업로드 대상에서 제외한다.
2. Vercel에서 프로젝트를 만든다. Git 저장소 연동 또는 CLI 배포 중 하나를 선택한다. Framework는 Other, Output Directory는 `public`, Node는 24.x다.
3. [설정 문서](01-project-setup.md)의 환경변수를 Preview 환경에 등록한다. 로컬 `.env.local`이 자동으로 운영에 설정된다고 가정하지 않는다.
4. 처음 배포해 고정 Preview 주소 또는 사용할 배포 주소를 확인하고 그 정확한 Origin을 `APP_ORIGIN`으로 지정한 뒤 다시 배포한다. 주소가 바뀌면 설정도 맞춘다.
5. `/`는 HTML, `/api/feedback`은 JSON인지 확인한다. API가 index.html로 바뀌거나 404이면 Output Directory·루트 api 폴더·rewrite 설정을 점검한다.
6. 실제 이미지 편집, 글 생성, PNG 다운로드, 피드백 저장·새로고침을 확인한다. Preview 보호 설정이 평가자의 접근을 막는지도 확인한다.

### Production

1. Production 환경에 전용 키·DB·생성 한도를 등록한다. `GENERATION_ENABLED=true`와 Vercel 시스템 환경변수 자동 노출을 확인한다. 별도 운영 도메인을 지정할 경우 `APP_ORIGIN`에 정확한 HTTPS 출처를 설정한다.
2. 같은 커밋과 잠금 파일로 Production 배포한다. Vercel 프로젝트에서 Node 24.x·Fluid Compute·생성 함수120초 설정이 반영됐는지 확인한다.
3. 실제 HTTPS 도메인에서 아래 배포 완료 항목을 확인한다. 환경변수를 바꾸면 새 배포로 반영됐는지 확인한다.
4. 명시적으로 지정한 운영 도메인이 바뀌면 `APP_ORIGIN`을 갱신하고 다시 배포한다.

## 6. 배포 보안 헤더와 운영

정적 페이지에는 다음 기준의 HTTP 응답 헤더를 `vercel.json`에 설정한다. 외부 글꼴·스크립트를 추가하지 않는 현재 구조의 기준이다. 실제 브라우저 콘솔에서 기능 차단 여부를 확인한다.

```text
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' blob: data:; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

인라인 이벤트 핸들러, CDN SDK, 외부 폰트 링크를 넣어 CSP를 느슨하게 만들지 않는다. Canvas/Blob 다운로드와 같은 출처의 피드백 첨부 이미지 표시가 CSP 아래에서 작동하는지 확인한다. `/api/*`에는 `no-store`를 유지한다.

운영자는 오류 코드·요청 수·외부 사용량을 확인한다. 하루 50회는 성공 이미지 수나 원화 비용 상한이 아니다. 공급자 프로젝트의 사용량 알림도 설정하고 실제 비용을 확인한다. 예상보다 요청이 많으면 `GENERATION_ENABLED=false`로 생성만 중지하고 새 배포에 반영한다. 한도나 타임아웃을 무작정 높이지 않는다.

화면 오류가 있으면 이전 정상 Vercel 배포로 롤백할 수 있다. DB는 배포 롤백으로 되돌아가지 않으므로 기존 데이터를 지우는 마이그레이션을 사용하지 않는다. 피드백 운영 삭제는 Supabase Dashboard에서 대상 행을 확인한 운영자만 수행한다.

## 7. 제품 배포 완료 체크리스트

- [ ] 실제 HTTPS 배포 URL과 배포한 커밋을 기록했다.
- [ ] 이미지 첨부 AI 편집 1회와 프롬프트 생성 1회를 실제 API로 확인했다.
- [ ] 픽셀 옵션 변경·미리보기·1024 PNG 다운로드가 동작한다.
- [ ] 로그인 없이 피드백을 보내고 새로고침·다른 브라우저에서 볼 수 있다. 동의해 첨부한 AI 결과와 프롬프트도 표시된다.
- [ ] 20개를 넘는 피드백을 최신순으로 끝까지 읽을 수 있다.
- [ ] 오류·중복 제출·DB 장애·요청 제한·키 미노출을 확인했다.
- [ ] 모바일·키보드·초점·문구를 확인했다.
- [ ] 테스트 결과와 미검증 항목을 구분해 기록했다.

최종 구현 보고에는 `완료한 기능 / 실행한 테스트와 결과 / 실제 외부 연동 여부 / 배포 URL / 남은 작업`을 포함한다. 소스코드만 작성하고 이 체크리스트를 통과하지 못했다면 `구현 중` 또는 `외부 연동 미검증`으로 보고한다.
